# Account persistence

This ticket adds an internal JPA account persistence layer, not signup, login, JWT verification,
profile endpoints, or frontend integration. Supabase owns authentication and passwords.

## Schema and deployment status

The project owner successfully applied
[V001__create_users.sql](db/migrations/V001__create_users.sql) manually in Supabase SQL Editor,
which reported `Success. No rows returned.` The owner confirmed that `public.users` exists with
all nine expected columns and the foreign key from `public.users.id` to `auth.users.id`.
RLS is enabled by the applied migration, which also revokes table privileges from `PUBLIC`, `anon`,
and `authenticated` and creates no browser policies. This deployment record is based on the owner's
confirmation and the applied script; the coding agent did not connect to or modify Supabase.

V001 is already applied to that project: **do not rerun it there or edit the applied migration**.
`public.organizations` remains outside this ticket. The nine column definitions follow
[the approved model](../docs/data-model.md#users). The approved ticket decisions are:

- `id` is supplied from a trusted Supabase Auth identity. No UUID is generated by this layer.
- The Auth FK uses `ON DELETE NO ACTION` and `ON UPDATE NO ACTION`. Deleting an Auth identity with
  an application account requires a future, reviewed account-deletion workflow.
- Email uniqueness is exact-value PostgreSQL `VARCHAR` uniqueness. Values are not lowercased or
  trimmed; case-insensitive uniqueness, email verification, and email synchronization are future
  decisions. Callers must pass the trusted Auth email, not an arbitrary identity assertion.
- `organization_id` is nullable with no FK because `public.organizations` does not exist. The
  standard-account creation service always leaves it null. Do not use the column for organization
  assignment until its relationship, FK, and authorization are implemented in a separate ticket.
- `created_at` is a database-generated `TIMESTAMPTZ DEFAULT NOW()`, mapped as `Instant` and read back
  on insert. It is not accepted as a service input or updated by JPA.
- RLS is enabled and `PUBLIC`, `anon`, and `authenticated` have no table privileges. No browser
  policies are created. JDBC authorization remains a backend responsibility, including for
  connections that bypass RLS.

The full application design still includes an organization FK; its omission here is a deliberate,
approved deferral rather than a change to that design. The decision register referenced by the
specifications is missing from this checkout. D02 (organization roles), D07 (Auth lifecycle), and
D09 (broader access policy) remain unresolved beyond these bounded ticket decisions.

## Manual migration procedure

The following procedure is for a fresh development project where V001 has not been applied.
For the existing Supabase project, retain V001 as deployment history and use a new, reviewed
version for future schema changes.

1. Review the complete SQL, confirm the intended Supabase project, and reconfirm the target table
   is absent. The script deliberately fails on an existing table rather than ignoring schema drift.
2. After separate deployment authorization, run the complete script in Supabase SQL Editor as the
   database owner. It requires Supabase's existing `auth.users`, `anon`, and `authenticated` roles.
   It creates only `public.users`, not organizations or Auth identities.
3. Record the version, commit/revision, application date, project, and operator in the team's
   deployment record. Do not rerun an applied version; prepare reviewed additive migrations for
   subsequent changes. No migration framework or automatic application is configured.
4. Inspect the nine columns, primary/unique/check/FK constraints, RLS, and grants. Configure a
   reviewed backend database role separately if not using the existing owner connection. A
   non-owner role needs schema usage and appropriate table privileges plus an explicit RLS access
   strategy; simply granting table privileges will not bypass RLS.
5. Verify persistence in an authorized development environment before production account use.
   Do not create accounts for a smoke test in production automatically.

The script is transactional; a failure aborts the transaction. There is no destructive rollback
script. Hibernate uses `ddl-auto=none`, SQL initialization is disabled, and startup performs no
schema migration/validation or JDBC metadata lookup. Consequently, successful startup and
`GET /api/health` do not prove this migration has been applied or account persistence works.

### Render account-table access

Keep the existing `prod` profile and `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, and
`SPRING_DATASOURCE_PASSWORD` settings. The JDBC URL must use `sslmode=require` for encryption, or
`sslmode=verify-full` with `sslrootcert` pointing to a readable absolute CA file for certificate and
hostname verification. No connection settings are changed by this ticket.

An owner connection normally bypasses RLS; the browser-role revocations do not remove the owner's
direct privileges. A restricted backend role needs schema usage, SELECT/INSERT table privileges,
and applicable RLS policies unless it has RLS-bypass privileges. Confirm the effective Render role
and access separately before deployed account use. The integration suite verifies the migration's
browser restrictions, not the live Render role's permissions.

## Internal service contract

`edu.gatech.sip6321.account.UserService` is available with the `database`, `prod`, or `render` profile.
It provides:

- `createStandardAccount(authUserId, email, firstName, lastName)` in a write transaction;
- `getById(id)` and `getByEmail(email)`, throwing `AccountNotFoundException` if absent;
- `existsById(id)` and `existsByEmail(email)` in read-only transactions.

Creation fixes the role to `STANDARD`; it accepts no role, organization, timestamp, or password.
It validates required values and documented column lengths without inventing email/blank-text
normalization rules. Nullable profile fields initially remain null. The repository supports
inherited save/UUID lookup/existence operations and derived email lookup/existence operations.
An assigned UUID uses `Persistable.isNew()` so a newly constructed record inserts and cannot merge
over an existing account.

Prechecks reject existing UUIDs/emails. Flushed database unique violations on `users_pkey` and
`users_email_key` are translated to a sanitized `DuplicateAccountException`, including insert races.
Other integrity failures remain `DataIntegrityViolationException` (for example a nonexistent Auth
identity), not duplicate-account errors. All creation failures roll back. A failed transaction must
not be reused; retry only by starting a new service call. The service does not log account data;
Hibernate SQL, binding, extraction, and JDBC error diagnostics are disabled because driver errors
can include values. Future controllers must sanitize errors and must not log raw exception chains.

There is no public account API. A future authenticated caller must verify identity before using
this internal service; an existing Auth FK proves existence, not the caller's authorization.

## Future signup coordination

Register through Supabase Auth, follow the separately approved email-verification/session policy,
and derive the trusted UUID and email through that integration. Then call this service with those
values. Never create or alter `auth.users` through JDBC, trust client-selected roles, or create a
replacement UUID. Supabase registration and the application transaction are separate operations.
If profile creation fails after Auth succeeds, keep the identity and provide an explicit
retry/reconciliation path; do not silently treat a duplicate as success or delete the Auth identity.
An actual retry may recognize an already-created account only after verifying that it belongs to
the authenticated identity. Signup, retries, email synchronization, and JWT verification are not
implemented by this ticket.

## Verification

From `backend/`:

```sh
./mvnw verify
./mvnw -Ppostgres-it verify
```

The first command runs all ordinary tests, checks Java formatting, and builds the JAR without
Supabase or Docker. The second additionally runs `UserPersistenceIT` through Maven Failsafe. It
requires Docker and permission to pull `postgres:17-alpine`; requesting this profile without Docker
fails rather than silently skipping persistence verification. The integration test starts a
disposable PostgreSQL container, supplies its own JDBC properties, creates a minimal Auth/role
fixture **only there**, and executes the actual versioned migration. It never uses external
Supabase credentials. The fixture lives in `src/test/resources/account-test-bootstrap.sql` and must
never be applied to Supabase.

Integration tests cover all nine mappings, timestamps, nullable profiles, repository and service
operations, duplicate UUIDs/emails, insert rather than overwrite behavior, missing accounts,
required columns/lengths/role values, Auth existence/deletion, and browser access restrictions.
Unit tests cover duplicate race translation and preservation of other integrity errors. The Auth
fixture verifies PostgreSQL FK behavior, not the complete managed Supabase Auth service.
